Propósito Clínico y Arquitectura del Sistema

💡 Idea Central: Estimación preventiva no invasiva del riesgo de enfermedad cardiovascular mediante 13 biomarcadores clínicos estandarizados (Dataset UCI Cleveland), orquestado sobre una arquitectura ligera y desacoplada.
Fundamentos Clínicos & Tecnológicos UCI Heart Disease
  • 1
    Problema Abordado: La cardiopatía isquémica es la principal causa de mortalidad global. La detección temprana mediante triaje asistido reduce drásticamente eventos coronarios agudos.
  • 2
    13 Variables Médicas Clave: Edad, sexo, tipo de dolor torácico (cp), presión arterial en reposo (trestbps), colesterol sérico (chol), glucemia en ayunas (fbs), ECG en reposo, frecuencia cardíaca máxima (thalach), angina inducida por ejercicio, depresión ST (oldpeak), pendiente ST, vasos fluoroscopia (ca) y thal.
  • 3
    Stack Desacoplado: Frontend reactivo con Streamlit, capa de inferencia determinista con scikit-learn serializado en joblib, y portabilidad 100% aislada en contenedor Docker.
Arquitectura de Capas de la Solución Zero-Latency Ingestion
UI
Capa de Presentación (Streamlit Web UI)
Formularios clínicos organizados en cuadrículas reactivas con validación inmediata en cliente.
VAL
Capa de Validación Fisiológica (app.py)
Filtro de integridad que verifica rangos biológicamente válidos (e.g. presión 80-250 mmHg).
ML
Pipeline de Inferencia (scikit-learn)
Imputación mediana + StandardScaler + Regresión Logística regularizada L2.
RES
Reporte Clínico y Semáforo
Probabilidad porcentual continua (0-100%) clasificada en Bajo, Moderado o Alto Riesgo.

💡 Idea Central: Los modelos de ML sufren degradación temporal (Data Drift y Concept Drift). El pipeline automatizado reentrena periódicamente los domingos a las 03:00 UTC sin requerir intervención humana.
Orquestación y Disparadores del Ciclo GitHub Actions Cron
  • 1
    Disparador Programado (Cron): Ejecución fija semanal mediante la expresión 0 3 * * 0 (cada domingo a las 03:00 UTC), momento de bajo tráfico operativo en la infraestructura clínica.

    Ejecución Manual Bajo Demanda (workflow_dispatch): Permite a los ingenieros de datos disparar el pipeline con un solo clic ante la llegada de nuevos lotes de información o auditorías extraordinarias.
  • 3

Regla de Promoción Estricta y Simulador Interactivo de Decisión

💡 Idea Central: El nuevo modelo compite bajo igualdad de condiciones. Solo se promueve si supera al modelo activo por un margen mínimo estricto (+0.001 ROC-AUC); de lo contrario, se preserva el modelo actual sin alteración. ¡Experimenta con el simulador interactivo en tiempo real!
Criterio Matemático de Decisión Tolerancia = 0.0010
ROC_AUC(Challenger) > ROC_AUC(Champion) + 0.0010
  • ✓
    Supera el Umbral (> 0.8910): El candidato es declarado nuevo Champion, se le asigna versión incremental (e.g. v4), se serializa el binario y se actualiza el alias productivo.
  • ✕
    Empate o Inferior (≤ 0.8900): Se activa el Descarte Seguro (Safe Discard / Rollback). El binario en producción permanece intacto, evitando regresiones por datos ruidosos.
  • ~
    Filtro de Ruido Numérico (0.8901 - 0.8910): Mejoras menores a 0.001 (0.1%) no justifican un despliegue, asegurando estabilidad operacional.
*Implementado en función pura decide_promotion(champion, candidate_metrics) en retrain_pipeline.py.

Filosofía y Disparadores del Pipeline CI

💡 Idea Central: Cada cambio introducido al repositorio es sometido a un riguroso 'Quality Gate' automático en GitHub Actions, impidiendo que código roto o modelos defectuosos alcancen la rama principal.
Disparadores Operacionales (.github/workflows/ci.yml) Trigger Matrix
  • 1
    Push a la rama 'main': Valida que las integraciones directas o merges mantengan la suite de 21 tests verde y gatilla el job condicional de despliegue a producción.
  • 2
    Pull Request contra 'main': Funciona como barrera infranqueable de revisión. No permite fusionar ramas si un solo test unitario, funcional o de build falla.
  • 3
    Entorno Homogéneo y Caché: Ejecución sobre runner virtualizado ubuntu-latest con Python 3.11 y caché inteligente de dependencias pip para optimizar tiempos.

Caso 2: Descarte Seguro y Preservación de Producción

💡 Idea Central: Blindaje ante datos ruidosos o modelos degradados. Si el candidato resulta inferior, empata o mejora por debajo de la tolerancia (+0.001), se rechaza y producción queda 100% intacta.
Aserciones en Código (3 Sub-escenarios) TestMaintenanceCase2NoPromotion
test_maintenance_ci.py (Caso 2)
# Subcaso 2.1: Modelo claramente inferior (0.8500 < 0.8900)
assert decide_promotion(CHAMPION, {"roc_auc": 0.85}) is False

# Subcaso 2.2: Empate numérico exacto (0.8900 == 0.8900)
assert decide_promotion(CHAMPION, {"roc_auc": 0.89}) is False

# Subcaso 2.3: Mejora marginal insignificante (+0.0005 < 0.001)
assert decide_promotion(CHAMPION, {"roc_auc": 0.8905}) is False
Mecanismo de 'Safe Discard' en GitHub Actions No-Op Seguro
1
Rechazo de Promoción Limpio
El script emite mensaje explicativo de descarte y finaliza de manera controlada.
2
Detección de No Cambios (git status)
El paso Detect changes verifica que los archivos de model/ no sufrieron alteración (output: changed=false).
3
Cancelación Segura de Deploy
Los pasos de commit y despliegue SSH son ignorados condicionalmente, asegurando cero riesgo de regresión en producción.
